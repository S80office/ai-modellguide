The Model Compass

The right AI model for the right task — not the one you're used to, not the priciest one. The one that's enough, at the lowest cost for the right result.

Last verified: August 17, 2026 Owner: AI Lead function Covers: Claude · GPT · Gemini
01 — The core thesis

Model choice isn't one decision — it's three

Match the model's weight to the task's complexity and the consequence of a mistake. Never habit, never "whichever one happens to be open".

  • Start low, escalate on friction. If the model misses the same type of task twice, switch tiers — don't keep rewording the same prompt forever.
  • Cost is measured per correct answer, not per call. A cheap model that has to be re-run three times costs more than a pricier model that gets it right on the first try.
  • Tier comes before provider. Decide whether the task is fast/cheap, balanced, or frontier — then pick Claude, GPT, or Gemini based on what you've already procured and which tools they're integrated into.
02 — Quick test

Which tier does your task need?

Answer three questions about the task in front of you.

1. How complex is the reasoning required?
2. What does it cost if the model gets it wrong?
3. Volume and pace?
Tier 1 — Fast & Cheap Based on your answers, the fastest and cheapest tier is enough.
03 — The three tiers

Think in three modes, not model names

Tier 1

Fast & Cheap

Routine, high volume, low risk, latency-sensitive.

Use for
  • Summaries & classification
  • Autocomplete, boilerplate code
  • Formatting, simple rewrites
  • Chatbots with bounded answers
Avoid for: multi-step reasoning, code that goes straight to production without review.
Tier 2

Balanced

The default mode for most day-to-day work.

Use for
  • Daily coding, refactoring, debugging
  • Requirements analysis, user stories, test cases
  • Content headed for review
  • Most agentic tasks
Avoid for: high-stakes architecture decisions, very long or contradictory context.
Tier 3

Frontier / Max

High complexity or high consequence of error — rare, but important.

Use for
  • Architecture decisions and hard-to-pin-down bugs in tightly coupled code
  • Security-critical or legally sensitive code/text
  • Long agentic workflows with many steps
  • Strategic documents with wide reach
Avoid for: high-volume, low-risk tasks — a waste of money and latency.
Common trap

Codebase size is not the same thing as complexity. A large but modular codebase where the task only touches one well-scoped part rarely needs Tier 3 — what actually drives the tier up is how tightly coupled the code is: hidden dependencies, unclear boundaries, side effects that are hard to verify. A small but tangled legacy module can be Tier 3 even when a huge, well-structured monorepo service isn't.

If the task needs a lot of code loaded in at once (e.g. a repo-wide migration), that's mainly a context-window and workflow question, not raw model power. Split the work per module across several Tier 2 calls instead of automatically reaching for the most expensive model.

Tier tells you how much power — this tells you what kind

The tiers in section 03 are about how much model a task needs. Providers have also built different kinds of strength, regardless of tier — that determines who you pick, not just how powerful.

A snapshot as of August 2026 — providers often catch up with each other on individual points within a few months. Use the table to pick a direction, not as a permanent verdict.

Anthropic — Claude

Reliability in long, agentic workflows

  • Low variance across repeated runs — important for automated pipelines and unattended agent workflows.
  • Deepest integration through a dedicated product pair for different roles — Claude Code for developers, Claude Cowork for non-technical knowledge workers — a shorter path from model to actual work than a general chat window.
  • Strong safety/compliance profile, often the first choice in regulated industries.

OpenAI — GPT

Broadest ecosystem, fastest with new modalities

  • Largest third-party ecosystem (GPTs, plugins, connectors) and an established Azure procurement path.
  • Often first to production with new modalities — voice, image, and video in the same interface.
  • Strong generalist when a task mixes several modalities in one flow.

Google — Gemini

Most context per dollar, deepest into Workspace

  • Multimodality built in from the ground up — not added later.
  • Largest context window relative to price — good for long documents, code repos, or video material.
  • The natural choice when data and tools already live in Google Workspace/Cloud or need grounding in Search.

Deep dive: Claude Code vs. ChatGPT Codex

This question comes up often, specifically about the two leading coding agents. Neither wins outright — they're built for different ways of working.

Dimension Claude Code ChatGPT Codex
Where the code runs Runs locally in your terminal, reads the filesystem directly — code never leaves your machine. Matters under NDA or with proprietary code. Cloud sandboxes by default (a CLI exists too) — good for asynchronous tasks you hand off.
Strength Code quality and repo-wide refactors — rated cleaner in blind comparisons in most cases. Speed, autonomy on terminal tasks, and token efficiency per task.
Context window Up to 1M tokens. 200K tokens.
Multiple agents at once Agent Teams — several agents share a task list and talk to each other. Up to 8 parallel subagents in isolated cloud sandboxes.
Pick this when Hard multi-file refactors, deep IDE integration, code that can't leave the machine. Async PRs, sandboxed execution, per-task cost is the deciding factor.
More tools in the landscape

The model is the engine — the tool wrapped around it decides how the work actually feels. Beyond Claude Code and Codex, there's also: AI IDEs (Cursor, GitHub Copilot in VS Code/JetBrains) that pull context from open files in the editor; more CLI agents (Gemini CLI) that, like Claude Code and Codex CLI, work close to the terminal against your own codebase; cloud-based/asynchronous agents (Google Jules, GitHub Copilot's cloud agent, Devin) where you hand off a ticket and get back a finished pull request; and open-source alternatives (OpenCode, Aider) for teams that want to own the infrastructure or switch models freely.

Regardless of tool: keep project instructions in an AGENTS.md or CLAUDE.md at the repo root. The format is now shared across most agents — the instructions carry over no matter which tool a developer picks.

One exception worth noting: GitHub Copilot is no longer its own model family. Since Copilot got model selection, users can pick Claude (Opus/Sonnet/Haiku), GPT, or Gemini from the model menu, depending on their Copilot plan — the same tier logic from the rest of this guide applies there too, just embedded in a dropdown instead of a tool switch. Since June 2026 it bills per token converted into "AI credits" (1 credit = $0.01), gated by the plan's quota.

06 — By role

Same compass, different vantage point

Manager / Lead

Steer with policy, not individual calls

  • Set Tier 2 as the org default. Require a short justification for Tier 3 at volume — not for one-off cases.
  • Encourage Tier 1 for internal tools, batch jobs, and automation where no one reads every answer.
  • Track cost per model tier quarterly, not just total spend — it shows where the team is over- or under-escalating.

Developer

Escalate on friction, not habit

  • Tier 1: autocomplete, boilerplate, simple rewrites.
  • Tier 2: the default for daily coding, debugging, refactoring.
  • Tier 3: architecture, hard bugs, large context, agentic workflows with many dependencies. Two failed attempts at Tier 2 = switch tiers, not prompts.

PM / Business Analyst / PO

Choose by use case, not model name

  • Tier 1: meeting notes, summaries, status updates.
  • Tier 2: requirements writing, user stories, structured stakeholder analysis.
  • Tier 3: strategic documents, complex stakeholder analysis, or decision material with wide reach and consequence.
07 — Keeping it current

Models change every month. The principles don't.

Separate what's stable from what's volatile — otherwise the whole guide goes stale every time a provider ships a new model.

Stable — rarely changes

  • The core thesis and the three questions (complexity, consequence, volume)
  • The three tiers and what they mean
  • The role guides (Manager / Developer / PM)

Volatile — needs a cadence

  • The table in section 04 (model names and pricing)
  • The strengths table in section 05 — who leads at what changes at least as often as price
  • Owner: a named person with a recurring calendar reminder — not "someone should do this"
  • Cadence: on every major model release from Anthropic, OpenAI, or Google, otherwise quarterly

Design out hardcoding in tooling

Reference tier-fast, tier-balanced, tier-frontier in internal configs, prompts, and guidelines — not exact model names. When a provider swaps a model, you update a single mapping instead of every place that points at a specific model name.

Trust the source, not the search result

Use the providers' own pricing pages for actual decisions. Third-party trackers (used for the table above) are good for a quick overview, not for procurement or budget.
